# 放下我执，让 Agent 进场：我终于理解了 Harness 工程

在疯狂燃烧了 3 亿 Token 后，今天开始使用新的生产环境工作。

以前的工作流是：

> 人提问 → LLM 生成 DSL → DSL 执行 → 出结果

现在更像是：

> 人提问 → Agent 理解目标 → 读取数据、脚本、测试、文档 → 在真实工作环境中修改或调用工具 → 直接产出结果

今天用下来，体验变化非常大。

mashang，这个为工作部署的项目，也正式从 **自定义 Agent** 迈向了 **Data Workspace Agent**。

---

## 1. Data Agent 的三个实践阶段

我对 Data Agent 的实践观察，大致可以分为三个阶段。

### 第一阶段：Text2SQL

最早的模式很简单：

> 人提问 → LLM 生成 SQL → 数据库执行 → 返回结果

本质上是让 LLM 直接驾驶数据库。

但里面的坑巨多。企业里的各种业务口径复杂、矛盾，表结构也不总是清晰。且有一个后视镜来看最大的 Bug，在彼时已经有 DeepSeek 的 Resoning 概念后，为什么还做这么弱智的东西？

### 第二阶段：LLM 生成 DSL

后来我开始转向 DSL Runtime。

核心思路是：

> 不让 LLM 直接操作数据库，而是通过 OLAP 模型和 DSL 操作分析语义。

我一度认为这是非常好的思路，并且它也确实在过去半年带来了实际的提效和工作减负。

这一阶段更像是：

> 给 LLM 修了一条稳定的数据分析高速公路。

### 第三阶段：Workspace Harness

现在进入第三阶段：

> 直接给 codingAgent 一个真实工作环境。

说白了，就是直接给 codingAgent 套一个文件夹。

结果发现，因为 codingAgent 本身具有出色的 runtime 能力，而且当前写代码需要的 token 成本几乎能有 98% 命中缓存，单次处理成本几乎都在 0.1 元以内。

**如果飞机票只比高速过路费高一点点，那干嘛还要修高速呢？**

---

## 2. 什么是 Harness 工程？

这个给 codingAgent 套文件夹的过程，本质就是所谓的 **Harness 工程**。

过去总想着自己设计 Runtime、Planner、DSL、Tool Router。

但现在越来越觉得：

> 不一定要重新发明 Runtime。

只要把真实工作流程整理成一个结构化 workspace，codingAgent 本身就能成为运行时。

一个 Harness 通常包含：

- scripts：可调用能力
- docs / AGENTS.md：操作说明
- tests / eval：反馈机制
- outputs：结果沉淀

于是工作方式从：

> LLM 生成分析逻辑

变成：

> Agent 驾驶一个数据工作空间

再进一步：

> workspace 本身成为一个可持续演化的生产系统。

所以我对 Harness 工程的定义是：

> 把原本依赖人工经验的工作流程，改造成可被 codingAgent 驾驶、验证和持续进化的生产系统。

---

## 3. 几个 Agent 概念怎么区分？

这里用“厂房”的类比最容易理解。

①workspace 是厂房，里面有数据、脚本、文档、测试和输出结果。

它不是 Agent，而是 Agent 工作的现场。

②CC、Codex、opencode 这一类 codingAgent 是万能工程师。它们进厂后，会看厂房怎么布置、生产线怎么跑、哪里缺测试、哪里需要重构、哪里需要修复。

③Deep Agents 更像自定义 Agent 的框架和基础设施。当厂房成熟后，可以用它组织不同分工的员工团队：有人负责接待用户，有人负责调度任务，有人负责执行分析，有人负责结果校验，有人负责记录上下文。

④而我自己命名的下一代 Agent 产品，也就是 runtimeV2，则是厂房成熟后的对外营业版本。它里面值守的是由 Deep Agents 组织起来的员工团队，同时具备用户接入、权限管理、任务调度、结果交付、日志追踪等能力。

⑤最后，XX Workspace Agent 不是一个具体产品，而是一种工作形态：

> Agent 在 workspace 中读取数据、调用脚本、运行测试、生成结果，并持续改进整个系统。

用一句话总结：

> codingAgent 负责建厂；Deep Agents 负责组织员工；runtimeV2 负责对外营业；Workspace Agent 是整套系统跑起来后的工作形态。

## 4. 新生产要素改变最优解

更深一层看，真正的变化不是：

> 我原来的方案不好，现在换一个 AI 工具。

而是：

> **当 AI 成为新的生产要素后，最优解本身会发生变化。**

原来基于“人类独自设计系统”的前提，得出的最优解可能是：

> 人设计 XX，AI 执行。

这里面有个隐藏假设：

> 人是唯一能理解系统、设计路径、组织流程的主体。

但现在 codingAgent 广泛进入人类社会后，一切都变了。

你不能在没有 AI 参与的情况下，预先设计出最适合 AI 参与的生产方式。

因为 AI 不是一个普通工具，而是一个会改变生产流程本身的变量。

它一旦进入系统，会改变：

- 哪些流程值得自动化
- 哪些抽象不再必要
- 哪些文档变得重要
- 哪些测试变成基础设施
- 哪些报错变成反馈机制
- 哪些人类经验应该外化
- 哪些路径应该由 Agent 自己探索

所以，真正的 Harness 工程不是“我设计一个给 AI 用的系统”，而是：

> **我构造一个 AI 可以参与改造的工作现场，然后在共同生产中找到更优系统。**

这也是从：

> AI as executor

变成：

> AI as co-designer of production system

旧范式是：

> 我设计系统，AI 执行任务。

新范式是：

> 我定义目标和边界，AI 参与设计系统本身。

---

## 5. 最大的转折：放下以自己为中心的主观

最大的转折点，不是用了 opencode，也不是多了一个 workspace，而是：

> **我开始把以自己为中心的主观控制，让渡给 codingAgent。**

这也是 Harness 工程最深的一层。

表面看是：

> workspace + scripts + docs + tests + eval

但底层其实是：

> **把人脑里的隐性工作流，外化成 Agent 可观察、可操作、可反馈的环境。**

人保留：

> 目标判断、业务方向、价值判断、最终验收。

Agent 接管：

> 路径探索、文件阅读、工具调用、报错修复、测试验证、文档沉淀。

---

## 6. 放下我执，不是丧失主权

以自我为中心的特点就是，我们总是觉得有什么不好，都是因为“你不好”。

这个模型不好，那个框架不好，这个工具不好，那个 Agent 不好。

于是，我们要换一个模型，换一个框架，换一个工具，换一个 Agent，甚至换一个人。

> 最大的问题可能不是“它不好”，而是“我太主观”。

这，不就尴尬了吗？

AI 作为新的生产要素，本身不在旧认知范围内。

真正更好的方案，必须是在新的生产要素共同参与的情况下摸索出来。

这背后其实是“放下我执”。

但放下我执不是丧失主权。

放下我执不是没有“我”。

恰恰相反，它是更好地探索我、界定我、理解我。

因为真正的主权不是：

> 每一步都由我控制。

而是：

> 我知道什么必须由我决定，什么应该交给系统涌现。

在人 + AI 的新生产关系里，人可能要从：

> 我来规定路径；我来控制过程；我来设计所有环节；AI 只能执行。

转向：

> 我定义目标；我设定边界；我判断价值；我负责验收；AI 参与路径探索；AI 参与系统演化。

这不是削弱“我”，反而是让“我”更清楚。

因为我要逐渐学会区分：

- 哪些是我的目标
- 哪些是我的偏见
- 哪些是我的控制欲
- 哪些是我的审美
- 哪些是我的业务判断
- 哪些只是我过去经验形成的路径依赖

> **放下我执，不是没有我，而是终于知道“我”应该在哪里。**

这也解释了为什么今天 workspace 的体验会这么爽。
